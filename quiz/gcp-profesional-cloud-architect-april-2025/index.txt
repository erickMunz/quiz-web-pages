d:T44f,### Real-Time IoT Data Ingestion Architecture

When ingesting streaming data from thousands of distributed sources like IoT sensors, the architecture requires an asynchronous ingestion buffer capable of handling high throughput followed by a stream processor that can process data with low latency.

* **Cloud Pub/Sub** acts as a globally distributed message broker capable of handling millions of events per second with automatic scaling.
* **Cloud Dataflow** (built on Apache Beam) provides serverless, parallel stream processing, handling windowing, late-arriving data, and transformations before writing to sinks like BigQuery or Bigtable.

#### Why other options are incorrect:
* **Option A:** App Engine is designed for web applications, not stream processing.
* **Options C & D:** Relational databases (Cloud SQL) and batch pipelines (Cloud Storage + Cloud Scheduler) introduce bottlenecks and delay processing, making them unsuitable for real-time streaming requirements.

[Google Cloud Pub/Sub & Dataflow Architecture Guide](https://cloud.google.com/architecture/stream-processing-architecture)e:T5af,### Enterprise Multi-Project VPC Architecture

Google Cloud **Shared VPC** allows an organization to separate network administration from project administration. A central network team manages the **Host Project** (subnets, routes, firewalls, VPNs), while application teams manage their workloads in **Service Projects** connected to the Shared VPC.

```
+-------------------------------------------------------------+
|                       Host Project                          |
|  +-------------------------------------------------------+  |
|  |                     Shared VPC                        |  |
|  |  Subnet A (Dev)      Subnet B (Prod)   Firewall Rules |  |
|  +-------+---------------------+-------------------------+  |
+----------|---------------------|----------------------------+
           |                     |
+----------v----------+   +------v--------------+
|  Service Project A  |   |  Service Project B  |
|   (Frontend VMs)    |   |   (Backend GKE)     |
+---------------------+   +---------------------+
```

#### Why Shared VPC over alternatives?
* **VPC Peering (Option B):** Peering works well but lacks centralized governance, is subject to quota limits, and doesn't allow transitive routing.
* **Cloud VPN (Option D):** Using VPN between internal cloud projects introduces artificial latency, encryption overhead, and extra cost.

[Google Cloud Shared VPC Documentation](https://cloud.google.com/vpc/docs/shared-vpc)f:T417,### Hybrid Connectivity Options

When bandwidth demands exceed 5 Gbps, low latency is critical, and internet jitter is unacceptable, **Dedicated Interconnect** is required.

```
+-----------------------+                         +-----------------------+
| On-Premises Data Ctr  |  Direct Physical Link   | Google Edge Location  |
|   Router / Switch     |========================>|    Colocation Facility|
|                       |  (10Gbps or 100Gbps)    |    (VPC Router)       |
+-----------------------+                         +-----------------------+
```

#### Connectivity Decision Matrix:
* **HA Cloud VPN:** Encrypted over public internet, max 3 Gbps per tunnel.
* **Partner Interconnect:** Connection via a service provider (useful if under 10 Gbps and direct co-location isn't present).
* **Dedicated Interconnect:** Direct connection to Google facility; required for high-throughput, latency-critical enterprise backbones.

Standard IAM authorizes *who* can access a resource, but it does not restrict *from where* or *to where* data can move. 

```
+--------------------------------------------------------------+
|                    VPC Service Perimeter                     |
|                                                              |
|   +-------------------+              +-------------------+   |
|   | Compute Engine VM | ===========> | BigQuery Dataset  |   |
|   +-------------------+ (Private API)| +-----------------+   |
|                                                              |
+--------------------------------------------------------------+
                               || (Blocked: Copy to external bucket)
                               v
                     [ External GCP Bucket ]
```

* **Service Perimeters:** Restricts API access (e.g., BigQuery, Cloud Storage) to specific network origins.
* **Prevents Stolen Credential Abuse:** Even if an attacker steals valid IAM credentials, VPC Service Controls block API calls originating from outside the defined perimeter.

```
                                  [ Global Anycast IP ]
                                            |
                         +------------------v------------------+
                         | Global External HTTP(S) Load Balancer|
                         +------------------+------------------+
                                            |
                     +----------------------+----------------------+
                     |                                             |
           (Nearest & Healthy)                           (Failover / Overflow)
                     v                                             v
          +--------------------------+                  +--------------------------+
        | Instance Group (US-East) |                  | Instance Group (EU-West) |
        +--------------------------+                  +--------------------------+
```

* **Anycast IPv4/IPv6:** Routes requests via BGP Anycast to the closest Google Edge PoP.
* **Cross-Region Failover:** If the closest region suffers an outage or reaches capacity, the Load Balancer seamlessly redirects users to the next closest healthy region.
